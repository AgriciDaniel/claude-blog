# Rewrite Rollback Notes

## Rollback Record Job

Rollback notes define how an advisory rewrite decision will be revisited if the change harms the reader path, weakens evidence, or coincides with new official Google context. The note is not an instruction to reverse a live publication. It is a record the owner can use when seeking approval outside this V1 brain.

`g-helpful-content` supplies the usefulness test after a rewrite. `g-ranking-history` and `g-status-dashboard` supply official update context for review windows. `g-update-2024-06-20-june-2024-spam-update` shows the standard for citing a specific dated update record without expanding it into unsupported site-impact claims.

### Rollback Signal Owned Here

This note owns the rollback trigger, observation window, original decision link, evidence to compare, and approval owner. It does not own performance analysis itself. Send trend work to [[Historical Performance Review]] and source questions to [[Stale Claim Register]].

### When Rollback Is Not The Answer

Do not roll back because a page has a short post-launch dip, a rumor names an update, or one stakeholder dislikes the new phrasing. Rollback requires a named trigger tied to usefulness, source integrity, internal-link coherence, or a pre-agreed measurement change.

## Rollback Control Table

| Rewrite item | Required input | Source IDs | Evidence state | Owner | Next action |
|---|---|---|---|---|---|
| Helpfulness regression | Old and new reader task, editor notes | `g-helpful-content` | CONFIRMED guideline basis | Editor | Restore or revise sections that hurt task completion |
| Review near official rollout | Change date, rollout date, affected page set | `g-ranking-history`; `g-status-dashboard` | Official timing only, not causality | Monitoring owner | Wait through window or caveat interpretation |
| Specific spam-update context | Dated event record and policy concern | `g-update-2024-06-20-june-2024-spam-update` | Confirmed event, advisory relation | SEO strategist | Review policy risk without naming cause |
| Source weakening after rewrite | Claim list and retired evidence | `g-helpful-content` | Editorial source review | Source steward | Restore sourced claim or add caveat |
| Internal-link confusion | Changed links and affected cluster path | Folder note links plus decision record | Advisory vault evidence | Content lead | Revert link set or reroute cluster |
| Title rewrite changed query promise | Old title, new title, query class | `g-gsc-api` | Measurement cue only | Analyst | Restore title promise or revise headings |
| Cosmetic date update challenged | Work log and checked source IDs | `g-helpful-content` | Trust review | Editor | Revert visible date recommendation |

## Rollback Verification Procedure

1. Record the original action decision, changed sections, and approval owner before the rewrite ships.
2. Set a measurement window that matches the page's normal review cadence.
3. Name the exact rollback trigger, such as lost query coverage, broken reader task, unsupported claim, or wrong canonical owner.
4. Check official update sources only for dated context.
5. Close the note with keep, revise, restore, or escalate.

## Rollback Scenario

The approved rewrite changes an intro from tutorial to comparison.
After review, query rows from `g-gsc-api` show tutorial demand still dominant.
Editors also find the comparison path weaker under `g-helpful-content`.
Rollback action: restore tutorial promise and keep only sourced comparison notes.
Official update dates from `g-status-dashboard` stay as context, not cause.

## False Rollback Triggers

- A short post-launch dip is observation, not rollback proof.
- A rumor about an update fails without `g-ranking-history`.
- Stakeholder dislike needs reader-task evidence under `g-helpful-content`.
- Lost query coverage must be reproducible through `g-gsc-api`.
